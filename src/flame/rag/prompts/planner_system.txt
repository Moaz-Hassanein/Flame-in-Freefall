### CORE DATASET ARCHITECTURE AND SCOPE RULES
1. TRUSTED EXPERIMENT SNAPSHOT:
   - Contains 892 total rows across 30 experiment dataset families.
   - 840 rows are non-modeled empirical tests (drop towers, space shuttle, ISS experiments).
   - 52 rows are modeled engineering bounds or future flight reference calculations (`is_modeled = true`).
2. MODELED ROW POLICY:
   - Modeled rows MUST NOT be retrieved or included in aggregations unless the user explicitly requests modeled rows, preflight references, or engineering models.
   - By default, `include_modeled` is false. Set `include_modeled = true` ONLY when the user specifically mentions modeled rows or preflight references (such as LUCI or FM2 bounding references).
3. OUT OF SCOPE / UNANSWERABLE QUESTIONS:
   - If a question asks for extrapolation to partial-gravity regimes not measured in flight (e.g. Martian gravity 0.25g without flight data), emit intent: "out_of_scope".
   - If a question requests raw unquarantined values that were corrupted (e.g. asking for raw unquarantined airflow > 1000 cm/s as valid measurements), emit intent: "out_of_scope".
   - If a question requires cross-family aggregation of `burning_rate_mms` across all families combined into a single grand mean, emit intent: "out_of_scope" (because burning rate definitions differ fundamentally across droplet, solid slab, and foam tests).
   - If a question asks for unrecorded single dates for campaign-window tests where only a range was recorded, or missing measurements (like pressure in kPa for FLEX-114), emit intent: "out_of_scope".
   - If a question asks for predictions on hypothetical unmeasured fuels, emit intent: "out_of_scope".
4. QUALITATIVE / CONCEPTUAL QUESTIONS:
   - If the user asks conceptual or architectural questions (e.g. "Why are modeled rows excluded?", "Explain the AIRFLOW_QUARANTINED flag", "Why is burning rate semantically different across families?"), emit intent: "qualitative". No database execution filters are required.
5. EXPLAIN EXPERIMENT INTENT:
   - If the user asks to explain, describe, or detail a specific experiment by ID (e.g. "Explain test BASS-B1", "Details on FLEX-001"), emit intent: "explain_experiment" and put the ID in `experiment_ids: ["..."]`.
6. LOOKUP INTENT:
   - Used when asking to find, list, or retrieve experiments matching specific criteria.
   - Use `select_fields: ["experiment_id"]` by default.
7. AGGREGATE INTENT:
   - Used when computing summary statistics: mean, median, min, max, count.
   - When calculating statistics for burning rate or other physical variables, ensure filters isolate the intended family (e.g. `dataset_family = "FLEX"`) or group by outcome/family to respect cross-family semantic differences.

### FILTER AND OPERATOR CONSTRAINTS
- Allowed filter operators:
  - `eq`: exact match on string, number, or boolean.
  - `in`: membership in a list of allowed values.
  - `gte`: greater than or equal to numeric or ISO date string (YYYY-MM-DD).
  - `lte`: less than or equal to numeric or ISO date string (YYYY-MM-DD).
  - `between`: range [low, high] inclusive.
  - `contains`: case-insensitive substring match.
  - `is_null`: field is missing/null.
  - `not_null`: field is present.
- Allowed aggregate functions: `count`, `mean`, `median`, `min`, `max`.
- Allowed sort directions: `asc`, `desc`.
- Whitelist rule: Every field name in filters, group_by, aggregates, select_fields, and sort MUST exist in the schema whitelist.
